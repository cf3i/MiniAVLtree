# Wisdom

> 跨 issue 验证有效的可复用模式。
>
> 记录"为什么这样做有效"，而不是"做了什么"（那是 progress.md 的职责）。

## 维护规则

1. 只在 Stage 5（Reflection）写入，禁止在其他 Stage 追加
2. 每条必须有至少一个 issue_id 作为来源验证
3. 只写"在 X 场景下，Y 有效"，禁止写泛泛的"建议"或"最好"
4. 反例字段（不适用时）为必填——没有边界的模式会被过度泛化
5. 只追加，不修改历史条目

## 记录模板

```markdown
## W-00X 标题

- 来源：<issue_id> / PR 链接
- 适用场景：
- 模式描述：
- 反例（不适用时）：
```

## 模式记录

## W-001 浏览器功能与回归脚本共用一份核心逻辑

- 来源：`1-html-avl-visualizer` / https://github.com/cf3i/MiniAVLtree/pull/1
- 适用场景：仓库需要新增一个轻量前端页面，但又没有现成前端构建系统，同时希望把页面的核心行为纳入 `issue_test` 做确定性回归。
- 模式描述：把树构建、状态转换、布局计算等核心逻辑写成浏览器 / Node 双用模块；浏览器页面只负责 DOM 渲染，`issue_test` 则直接在 Node 中加载同一份模块验证结果。
- 反例（不适用时）：如果页面强依赖框架运行时、浏览器专属 API 或异步网络交互，这种“单文件双用模块”会变得臃肿，应改用更明确的前后端分层或测试桩。
