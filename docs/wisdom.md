# Wisdom

> 跨 issue 验证有效的可复用模式。
>
> 记录"为什么这样做有效"，而不是"做了什么"（那是 progress.md 的职责）。

## 维护规则

1. 只在 Stage 5（Reflection）写入，禁止在其他 Stage 追加
2. 每条必须有至少一个 issue_id 作为来源验证
3. 只写"在 X 场景下，Y 有效"，禁止写泛泛的"建议"或"最好"
4. 反例字段（不适用时）为必填——没有边界的模式会被过度泛化
5. 只追加，不修改历史条目

## 记录模板

```markdown
## W-00X 标题

- 来源：<issue_id> / PR 链接
- 适用场景：
- 模式描述：
- 反例（不适用时）：
```

## 模式记录

## W-001 用同一份 JS 核心逻辑同时服务页面和 issue test

- 来源：`2-html-avl-visualizer` / [PR #2](https://github.com/cf3i/MiniAVLtree/pull/2)
- 适用场景：需要新增静态浏览器交付物，但仓库没有现成的前端测试框架，也不想为了一个页面引入浏览器自动化。
- 模式描述：将核心行为提炼到可被浏览器直接调用、也可被 Node `require` 的 JS 模块中；页面只负责采集输入和渲染，issue test 直接验证同一套导出函数的遍历、根节点和布局结果。
- 反例（不适用时）：如果项目已经有完整前端构建与端到端测试体系，或必须复用后端 / C++ 原生实现而不能接受一份前端镜像逻辑，就不应额外维护一套 JS 核心实现。
